# Plan 002 — Connect & Send

spec: [spec.md](spec.md)

## 기술 선택

| 선택 | 근거 |
|---|---|
| 기존 `connect_device` 흐름 끝에 전송을 이어 붙임 | 이미 `send_handshake()`를 그 자리에서 호출 중. 새 진입점을 만들면 두 경로가 갈라져 유지가 어려워진다 |
| 별도 버튼 대신 **스위치 + 메시지 유무** 조건 | 버튼을 늘리면 "어느 걸 눌러야 하나"가 생긴다. 메시지가 비면 안 보내므로 오발송이 구조적으로 막힌다 |
| 단계 시간 측정은 `datetime.now()` 차이 | 이미 로그 타임스탬프에 쓰는 모듈. 새 의존성 불필요 |
| `discover(timeout=3.0)` + `sleep(0.5)` | 기존 5s+1s에서 절반 이하로. 스캔 1사이클이 창 소모의 첫 항목이다 |

## 구현 접근

1. **`send_order()` 추출** — `send_data`(버튼 핸들러)에서 실제 전송 로직을 인자 없는
   코루틴으로 분리한다. 버튼과 자동 흐름이 같은 코드를 쓴다.
2. **`connect_device` 말미에 자동 전송 연결** — 핸드셰이크 성공 시에만 진행한다.
   `send_handshake()`가 현재 예외를 삼키므로 **성공/실패를 bool로 반환**하도록 바꾼다.
3. **단계 시간 계측** — `connect_device` 시작 시각을 잡고, 각 단계 후 경과를 로그에 남긴다.
   전체가 60초를 넘으면 경고.
4. **스위치 추가** — `auto_send_switch`를 Connection Information 헤더에 배치
   (기존 `write_response_switch` 옆).
5. **스캔 주기 단축** — `run_scan`의 timeout·sleep 값 조정.

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 자동 전송이 의도치 않은 주문을 보냄 | 메시지가 비면 전송하지 않음 + 스위치로 완전 차단 (FR-2/FR-3) |
| 핸드셰이크 실패 후에도 주문을 보내 이중 실패 | `send_handshake()` 반환값으로 게이트 (FR-5) |
| 자동 전송 중 사용자가 Send를 눌러 중복 전송 | 기존 `io_busy` 가드가 이미 막는다 |
| 스캔 주기 단축이 발견율을 떨어뜨림 | `discover` 3초는 광고 주기(수백 ms) 대비 충분. 실기기에서 확인 필요 |
| 상대가 주문 1건 후 서버를 내려 재전송이 항상 실패 | 상대측 제약. 자동 전송은 연결당 1회로 제한하고 문서에 명시 |

## 검증 방법

자동 테스트 없음. **Windows + Android 실기기 수동 시나리오**:

1. **정상 흐름** — 메시지에 `order_id=999` 입력 → 폰에서 "결제 시작" → Connect 클릭.
   기대: 로그에 `AT+CONNECT acknowledged` → `Response (AT+CONNECT): ... Connected`
   → `[AUTO-SEND]` → `Response (order): ... Order received`, 폰 화면에 "주문번호: 999".
2. **빈 메시지** — 메시지를 비우고 Connect. 기대: 연결까지만, 전송 로그 없음.
3. **스위치 OFF** — 메시지를 채우고 스위치를 끈 뒤 Connect. 기대: 전송 없음.
4. **핸드셰이크 실패** — 폰에서 "결제 시작"을 누르지 않은 채 Connect(또는 60초 경과 후).
   기대: 핸드셰이크 실패 로그 후 **주문 write 시도 없음**.
5. **시간 예산** — 1번 시나리오 로그에서 전체 소요가 60초 미만인지 확인.

로컬 정적 검증은 `python -m py_compile main.py`까지만 가능하다.
