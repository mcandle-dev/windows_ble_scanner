# SDD Feature — spec/plan/tasks 생성

새 기능·구조 변경을 구현하기 **전에** 문서를 만든다. 구현 요청이 함께 왔더라도
문서 작성 → 사용자 확인 → 구현 순서를 지킨다.

## 절차

1. `specs/` 아래 기존 디렉터리를 확인해 다음 번호 NNN을 정한다 (3자리, 0패딩).
2. 기능을 짧은 영문 slug로 요약해 `specs/NNN-<slug>/` 디렉터리를 만든다.
3. 아래 역할 분리를 지켜 3개 파일을 작성한다. 기존 spec(001, 002)의 형식을 템플릿으로 삼는다:
   - **spec.md** — 무엇을·왜. 배경, 사용자 시나리오, 기능 요구사항 표(FR-n + 수용 기준),
     비기능 요구사항, 범위 제외. 상태 배지(🚧 진행 중 / ✅ 완료) 포함.
   - **plan.md** — 어떻게. 기술 선택과 근거, 영향 범위(수정 파일), 리스크와 대응, 검증 방법.
   - **tasks.md** — 실행 단위. `- [ ] Tn.` 체크리스트, FR 참조 표기. 문서 갱신
     (DESIGN.md/CHANGELOG.md/README.md)과 실기기 검증 태스크를 항상 포함시킨다.
4. 작성한 spec이 `constitution.md`와 충돌하지 않는지 검토한다. 충돌하면 구현하지 말고
   사용자에게 보고한다.
5. 사용자에게 spec 요약을 보여주고 확인을 받은 뒤에만 구현을 시작한다.

## 구현 중·후

- 태스크를 끝낼 때마다 tasks.md 체크박스를 갱신한다.
- 구현 완료 시 spec.md 상태를 ✅로 바꾸고, DESIGN.md(현행 실체)와 CHANGELOG.md를 갱신한다.
- BLE 동작 검증은 이 환경에서 불가능하다(Windows 전용). 검증 시나리오를 정리해 사용자에게 전달한다.
